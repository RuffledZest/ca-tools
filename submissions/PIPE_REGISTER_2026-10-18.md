# Submission pipeline register, 2026-10-18

This register records the submission check built in /home/claude/pipe/ca-tools, a partial copy of github.com/chrispbsmolen/ca-tools. It lets strangers submit covering arrays by pull request and has the repository verify, record and credit them without the maintainer. Everything the check runs is Python standard library plus the C verifier ca_verify.c. R is not needed on the runner.

## Files

submissions/README.md is the submitter's guide in plain prose: the directory layout, the claims.csv header t,v,k,N,file,source_detail,credit,notes, the array text format, stair-step claim semantics, what happens on a pull request, the two outcomes, the screened status, how credit and source are written into the rows, the fork case, how to run the check locally, and the existence of the table page.

submissions/example/ is the worked example: CA_9_2_4_3.txt holds the textbook OA(9; 2, 4, 3) over GF(3) with rows (a, b, a+b, a+2b mod 3), and claims.csv claims it at t=2, v=3, k=4, N=9. The brief suggested copying table/arrays/CA_9_2_4_3.txt, but a verbatim copy has the same canonical hash as an existing MANIFEST entry and the duplicate rule (also required by the brief) would reject it. The example therefore uses a different 9-run array of the same parameters, which the check records as equals_best under the hash-suffixed name CA_9_2_4_3_9133df95.txt. The workflow never checks or records the example directory.

submissions/bergeron-rms-2026-10/ is the real test submission: the 20 array files from github.com/MichelBacon/covering-arrays-rms-extension at commit 2c4edea and a claims.csv with one row per file. The parameters come from the file names and were cross-checked against improvements.csv (N_new equals the file's N for all 20). source_detail is the repository URL, the commit and the file path; credit is "Mickael Bergeron"; notes carry the previous best, previous source and gain that the submitter reported. improvements.csv has 81 rows, but only 20 arrays exist (one per stair rung top); the v=19 rows have no arrays and are not claimed. The input directory /home/claude/bergeron_in was not present, so it was cloned from GitHub; HEAD is 2c4edea as stated.

tools/check_submission.py is the check. It takes a submission directory and options for the table directory, the ca_verify binary, threads, the per-array budget (default 20 minutes), an optional total budget, the screen threshold (default 1e10), the screen window count and width (20 and 30), the output directory, the pull request number, the stamp version and the date. It writes report.md, summary.json and, only when every claim passes, ca_table_rows.csv, manifest_rows.csv and arrays/ with the canonical files. With --apply it appends the rows to table/ca_table.csv and table/MANIFEST.csv and copies the canonical files into table/arrays; without --apply nothing under the table directory changes. It exits 0 when every claim passes, 1 otherwise, 2 on setup errors. A --selftest mode re-hashes every file in table/arrays and compares both the canonical hash and the raw file hash with MANIFEST.csv.

tools/render_table.py writes docs/index.html from table/ca_table.csv and table/MANIFEST.csv: the table's description, a link to submissions/README.md, counts (table rows, verified rows, screened rows, arrays on file, verified and screened arrays, community submissions), the generation date, a list of community submissions with credit, previous best and stamp, and for every (t, v) a collapsible stair-step of best known N with the evidence for each rung (verified rungs tagged with credit, source, stamp and hash prefix; screened rows listed but marked as not counted). No JavaScript, a small inline stylesheet with a dark mode, readable at 400 px (checked by rendering at 400 px). The page from the current table is about 1.4 MB with 120 (t, v) sections.

docs/index.html is that page generated from the current table on 2026-10-18.

.github/workflows/verify-submission.yml is the pull request check. .github/workflows/table-page.yml regenerates docs/index.html on every push to main (and on manual dispatch), stamping only the date so repeated pushes on one day do not create page commits, and commits the page if it changed.

## Exact rules

Parsing follows ca_verify.c: entries separated by spaces, tabs, commas or carriage returns; blank lines skipped; NA in any case, "-", "*", "x", "X" and -1 are don't-care. Unlike ca_verify, which silently skips unknown characters, any other token is an error. All rows must have the same number of entries. Symbols are 0-based when the smallest concrete symbol is 0 and the largest at most v-1, and 1-based (shifted down by one, as ca_verify does) when the largest is exactly v and the smallest at least 1. A range containing neither 0 nor v is rejected as ambiguous, and anything above v or below -1 is out of range. v is limited to 127 and v^t to 2^40 (ca_verify stores symbols in int8 and limits the tuple bitmap), and canonical lines must be under 65,000 characters (ca_verify's line buffer). Array files must be plain regular files with simple names in the submission directory, no symbolic links, at most 200 MB.

Canonicalization reproduces verify_pipeline.R::canon_serialize: 0-based integer symbols, one run per line, the k values separated by single spaces, "NA" for don't-care, "\n" after every line including the last, no header, no trailing whitespace. SHA-256 is taken over the UTF-8 bytes. The array is verified from this canonical text, so the hash and the verification refer to the same bytes. The hashes of the three files present reproduce their MANIFEST entries exactly: CA_9_2_4_3.txt 58193e6badbef08a1763767be047d94431301dcaf3ad96d836af2b1921c55ea9, CA_351_5_7_3.txt c63cef407119ef3ba7a9122c99c28f6d9c191f50fc5a77161aed7c4bfd42fba4, CA_357_5_194_2.txt 19399f52ba3aa2cbac5213705ddc601de7ecf800b79bed687d990709c040129a. The same CA_351_5_7_3 written 1-based, comma separated with CRLF endings hashes to the same value.

Duplicates are detected by canonical SHA-256 against MANIFEST.csv, against every array_sha256 in ca_table.csv (which also covers VERIFIED rows whose arrays are not in arrays/), and within the submission. A duplicate fails its claim before verification.

The comparison is stair-step: the best known N at (t, v, k) is the minimum N over rows of tier CITED or VERIFIED with the same t and v and k' at least k, exactly as table/ca_table.py best. N below it is exceeds_table, equal is equals_best, above is above_table (passes, recorded as verified with a note that it is not an improvement). With no row at all for (t, v, k' at least k) the claim is exceeds_table with a note. Claims in one submission are each compared with the table as it was before the submission; when several submissions are checked in one run, each sees the rows applied by the previous one.

Full versus screen: the estimated work is C(k, t) times v^t. When it exceeds the threshold (1e10 on the runner and by default) and k is above the window width of 30, the claim is screened. A claim checked in full that does not finish within its budget also falls back to the screen, with a fresh per-array budget bounded by the total. The screen takes 20 random sets of 30 distinct columns, drawn with Python's random.Random seeded by the first 16 hex digits of the array's hash, so anyone can rerun the same windows; each sub-array (all N rows, those columns) is verified exhaustively by ca_verify at strength t. Any gap fails the claim and reports the uncovered columns mapped back to the original column numbers with the missing values. If all windows pass, the status is screened, never verified. If the windows cannot all finish within the budget, the claim fails. Arrays with k at most 30 are never screened, since the only window would be the whole array; they get the full check and fail if it does not finish. This is the one place where the build departs from the literal brief ("or all columns if k <= 30"), because a single all-column window is an exhaustive check and the brief also says a screen must never be recorded as verified.

Naming: canonical files are CA_N_t_k_v.txt. If that name is already in MANIFEST.csv, in table/arrays, or earlier in the same submission with a different hash, the name becomes CA_N_t_k_v_<first 8 hex digits of the sha256>.txt, matching the existing CA_66_4_38_2_74dde85d.txt and CA_4_2_3_2_fa93338b.txt. The apply step refuses to overwrite an existing file.

Rows written: ca_table.csv rows follow the 14-column schema with minimal quoting and CRLF line endings like the existing file: t, v, k, N, tier VERIFIED or SCREENED, source_id S7, source_detail exactly as submitted, snapshot_id "pr-<number>" in the workflow or the slug locally, array_sha256, verify_stamp "ca_verify <short sha of the base commit, or 'tools' outside git> <date> github-actions" (outside Actions the machine tag is like Linux-x86_64, in the style of the existing "caverify 0.2.0 2026-08-23 Darwin-arm64"), entered date, notes, and empty lb and lb_evidence. Notes read "credit: <credit exactly as given>; <comparison with the previous best N, the k of the row that holds it, its tier, source_id, snapshot_id and source_detail>; [screen statement]; submission <slug>; <submitter notes>". MANIFEST.csv rows use R write.csv style (strings quoted, numbers bare, LF endings) with status exceeds_snapshot for exceeds_table, equals_best for equals_best, above_best for above_table (a new status value; the existing file only uses the first two), and screened for any screened claim.

## The workflow

verify-submission.yml runs on pull_request_target for opened, synchronize and reopened pull requests touching submissions/**. It uses pull_request_target rather than pull_request because a pull_request run from a fork gets a read-only token and could not even post the report; to make that safe the workflow never runs code from the pull request. It checks out the base branch (tools, ca_verify.c, table) into base/ and the pull request branch into pr/, reads pr/ only as data, builds ca_verify with cc -O3 -pthread, runs the self-test, and lists the changed files through the GitHub API. Any changed path outside submissions/ and table/, or any symbolic link under submissions/, fails the run. Every changed submission directory other than example is checked with 2 threads, 15 minutes per array, a total of 300 minutes for the pull request, and a screen threshold of 1e10, against a scratch copy of the base table with --apply. The job timeout is 340 minutes, inside the 6-hour limit. The reports are posted as one pull request comment with gh (truncated at 60,000 characters). If every claim passed, the scratch table replaces pr/table; if that changes nothing, the comment says the pull request already contains its rows; otherwise, for a branch in the same repository, the bot commits "Record submission <slug> in the table (verified by ca_verify)" and pushes to the pull request branch, and for a fork it uploads out/ and the updated table as the artifact table-rows-pr-<number> and says so in the comment. If anything failed, nothing is applied and the last step fails the job. Because the table is rebuilt from the base branch every time, reruns are idempotent and hand edits to table/ in a pull request are overwritten by the computed rows. The push uses the repository secret TABLE_BOT_TOKEN when it exists and GITHUB_TOKEN otherwise.

## One-time setup on GitHub

The maintainer must do four things once. In Settings, Actions, General, set workflow permissions to "Read and write" so GITHUB_TOKEN can push and comment (the workflows also request contents: write and pull-requests: write), and keep the default that requires approval before workflows run for first-time contributors if desired. In Settings, Branches, protect main and require the "verify" status check from the Verify submission workflow before merging. In Settings, Pages, serve from the main branch, /docs folder. Optionally, and recommended, create a repository secret TABLE_BOT_TOKEN holding a fine-grained token (or GitHub App token) with contents write on this repository: pushes made with GITHUB_TOKEN do not trigger new workflow runs, so without that secret the bot's own commit has no check of its own and a required check will show as pending on the new head; with the secret the push triggers a confirming run that passes with nothing to apply. Also regenerate table/ca_table.rda with ca_table.R::make_rda() from time to time, since the runner has no R and does not update it.

## Known limits

The runner has 2 cores and a 6-hour job limit. At about 8e7 units of C(k, t) times v^t per second on 2 threads (measured on strength 3 arrays), the 1e10 threshold means a full check of about two minutes, leaving room under the 15-minute budget for arrays whose N is several times v^t. The estimate ignores N, so arrays with N much larger than v^t (small v, high t) are underestimated: CA_357_5_194_2 (t=5, v=2, estimate 7.1e10) did not finish in 10 minutes here. Such arrays are screened by the threshold or by the budget fallback, at the cost of one wasted budget in the second case. A pull request is limited to 300 minutes in total, roughly 20 arrays that each need a full budget.

A screened array is not proven. Twenty windows of 30 columns test only a sample of the C(k, t) column sets; a defect confined to rare column combinations can pass a screen. SCREENED rows are kept out of the best known values for that reason and wait for someone to verify them in full elsewhere. Arrays that even the screen cannot finish within the budget (very large N or high t, where one 30-column window is already expensive) fail, and need a maintainer with a larger machine, who can run check_submission.py with a larger budget and --apply.

Pull requests from forks cannot receive the bot's commit with the default token; the rows travel as a workflow artifact and the maintainer applies them, or the submitter asks for a branch in the repository. If main moves while a submission is open, rerun the check after updating the branch so the rows are rebuilt on the new table; otherwise the appended lines may conflict. Every run posts a new comment rather than editing the previous one. The entered date is the date of the run, so a rerun on a later day rewrites the rows with the new date.

The check trusts the claim only as far as the array proves it: credit and source_detail are recorded exactly as given and are not verified. The verifier itself is ca_verify.c from the base branch, validated as described in the repository README and VERIFICATION_LOG.md; the stamp records the base commit so any row can be traced to the verifier version that minted it.
